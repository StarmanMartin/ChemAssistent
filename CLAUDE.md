# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
A small Ubuntu desktop app (Python 3, GTK 3 via PyGObject). A Chemotion icon in the GNOME top bar (Ayatana AppIndicator) opens a centered prompt; submitting it grows the window to the work area with a chat (`ChatPanel`) on the left and a result panel on the right. The agent is our own (`agent.py`, stdlib only) and talks to any OpenAI-compatible API (default: the KIT KI-Toolbox, or Google's Gemini API, or a local Ollama); the settings can instead pick a CLI agent (`cli_agent.py`: Claude Code, Codex) with the same tools. The agent reaches the Chemotion ELN only through its `execute_python` tool, whose code the user must confirm in the result panel — unless an auto-run mode is on (`config.AUTO_RUN_MODES`: `off`/`readonly`/`always`; `readonly` auto-runs snippets that `agent.looks_read_only()` clears). With a JupyterLab configured the built-in agent also has `execute_jupyter` (`jupyter.py`) for analyses and `start_jupyter_job` for long calculations (background jobs, `jobs.py`; their reports come back as a new turn), and both sides share a per-conversation exchange folder. Structure, config handling, settings app and install scripts are taken over from `~/Deveolop/private/vikunja-popups`. Until 2026-10 the app embedded the opencode TUI instead (see git history). There is no linter config; the tests are `tests/` (pytest, see below); only the Windows version has a build step (`windows/build.py`, see below).

## Architecture
- Platform split: `config.WINDOWS`; `config.FROZEN` is the PyInstaller build (this file's folder is then `_internal\`, so `HERE`, `WORKSPACE_DIR` and the SVGs resolve inside the bundle). Windows has no AppIndicator (`Gtk.StatusIcon`), no AF_UNIX in Python and no unix signals (`signal_add` is `None`). On Windows `main()` logs to `STATE_DIR/app.log` and writes the PID file (`app_control.py`, used by the settings' Start/Stop; `APP_PROCESS_NAMES`). Child processes (settings, runner, the app from the settings) start through `workspace.command(script, console)`: from source the current Python (python.exe/pythonw.exe on Windows), frozen the exes in `FROZEN_PROGRAMS`; the runner gets `creationflags=NO_WINDOW`. Otherwise the UI is the same on both platforms.
- `ipc.py`: for a second start of the app (`{"type": "show"}`), hotkey.py (`{"type": "hotkey"}`) and mcp_bridge.py (`{"type": "execute", "session", "purpose", "code"}`, answered with `{"text"}` once the card is decided; `RequestServer._serve` drops the 5 s timeout for it, `MAX_REQUEST_BYTES` is large for the code). Linux: Unix socket `SOCKET_PATH`, empty token. Windows: `127.0.0.1:<random port>` plus a random token, both in `ENDPOINT_FILE`; requests without the right token are dropped.
- `config.py`: `~/.config/chem-assistent/config.json` (Windows: `%APPDATA%`, state in `%LOCALAPPDATA%`) (0600, atomic writes), `load_config()` raises `ValueError` while URL/user/password are missing (`config_problem()`); `CHEMOTION_PASSWORD` overrides the password. Secrets (`SECRET_KEYS`: `password`, `ai_token`, `gemini_token`, `jupyter_token`, `jupyter_password`, `github_token`) live in the system keyring (`keystore.py`) when there is one: `save_raw_config()` stores them there (empty value = delete) and writes them empty plus `"secret_store": "keyring"`; if storing fails, or with `use_keyring: false` (`uses_keyring()`, the settings' switch; switching off also deletes the keyring entries), all stay in the file without the marker (the keyring is then ignored). `read_raw_config()` fills them back only with the marker (not with `secrets=False`, e.g. the hotkey); a non-empty value in the file wins; it returns a `RawConfig` dict whose `keyring_problem` says why the secrets from the keyring are incomplete ("" when they are). `_keyring_secrets()` caches by config.json's stamp (path, inode, mtime, size: a save in another process invalidates it) for `SECRET_TTL_S` (keyring-only edits), a failure for `SECRET_RETRY_S` (`retry=True` reads again at once); one thread (`_Reader`; any exception, not only `KeystoreError`, becomes the problem) reads everything with one `keystore.read_all()`, and in the app and the settings (`limit_main_thread_wait()`, `MAIN_THREAD_KEYRING_WAIT_S`) the main thread waits for a read it started at most that long, for one already running not at all — meanwhile the last secrets serve on while config.json is unchanged (a TTL refresh), else they are empty and the problem is `NOT_ANSWERED`. `load_config()` raises the problem (not "set the password"), and while it is set, saving would delete the secrets, so `setup_ai.py` saves nothing and the settings re-read with `retry=True` on Save and refuse otherwise (`_recover_secrets()`, every field of `secret_entries`, asserted against `SECRET_KEYS`). `save_raw_config()` runs under `_save_lock()` (`config.json.lock` next to the file, `fcntl.flock` / `msvcrt.locking`, shared by all processes, `OSError` after `SAVE_LOCK_WAIT_S`), so keyring and file of one save are written before the next one starts; it writes only the keys whose value differs from the (valid, error-free) cache, and with the keyring off deletes the entries at every save (also what a save that failed halfway left there); `save_raw_config(data, if_stamp=…)` checks the stamp inside the lock and writes nothing if config.json changed meanwhile; a failed file write drops the cache, and `_saves` counts the saves so that a read begun before one does not put its older secrets into the cache. The settings save in a thread (`_save_worker`: the keyring may wait for an unlock prompt, the lock for another program) and compute the storage note in one (`storage_location()` may probe the keyring). `migrate_secrets()` moves plain-text secrets (app start in a thread, `setup_ai.py`, any settings save), with `if_stamp`: a settings save during an unlock prompt wins. AI: `ai_url` (default `KI_TOOLBOX_URL`), `ai_token` (empty → env `KI_TOOLBOX_API_KEY`, `ai_token()`), `ai_model` (default `alias.complex-local`); `ai_problem()` is checked on submit and in the settings. `auto_run` is one of `AUTO_RUN_MODES` (unknown values → `off`) and the default mode for new conversations. `history_access` (default off; the settings' General tab) lets the agent read the saved conversations (`agent.base_roots()`, `workspace.HISTORY_PROMPT`). JupyterLab (optional): `jupyter_url` (empty = off; `load_config()` also empties it while `jupyter_problem()` complains), `jupyter_token` or `jupyter_password`, `jupyter_folder` (default `DEFAULT_JUPYTER_FOLDER`), `jupyter_verify_tls`; `Config.jupyter`. `EXCHANGE_DIR` = `STATE_DIR/exchange`. `agent` is one of `AGENTS` (`api`, `gemini`, `ollama`, `claude`, `codex`); each keeps its own keys (`AGENT_KEYS`: `gemini_url`/`gemini_token`/`gemini_model`, `ollama_url`/`ollama_model`, `<cli>_command`/`<cli>_model`), and `load_config()` puts the chosen one's into `Config.ai_url`/`ai_token`/`ai_model`/`agent_command` (so Gemini and Ollama are just the built-in agent with another URL and token; `agent_token()`: an empty token falls back to the agent's `TOKEN_ENVS` variable, `KI_TOOLBOX_API_KEY`/`GEMINI_API_KEY`). Gemini = `GEMINI_URL`, its OpenAI-compatible endpoint; the settings show `AGENT_WARNINGS["gemini"]` while it is chosen (free keys: Google may train on the data, except in the EEA/CH/UK). An empty CLI model is the CLI's default (`model_name()`); `cli_agent.cli_models()` fills the header menu (`CLI_MODELS` plus the `visibility: "list"` slugs of Codex's `~/.codex/models_cache.json`). The app starts anyway and reports problems in the prompt. `WORKSPACE_DIR` is `workspace/` next to the code; `SOCKET_PATH` is in `$XDG_RUNTIME_DIR` (AF_UNIX paths are limited to ~100 bytes).
- `keystore.py` (stdlib + PyGObject's `Secret` typelib, `gir1.2-secret-1`; nothing loaded before the first call, hotkey.py imports config): `backend()` once per process (a failure is probed again after `PROBE_RETRY_S`) — Linux `SecretService` (libsecret, schema `SCHEMA`, attribute `key`; available only with a `default` collection alias: a bare gnome-keyring-daemon, as under WSL, answers lookups with nothing and fails stores after ~15 s; every call is cancelled after `TIMEOUT_S` via `Gio.Cancellable`; `read_all()` = one `Service.search_sync` with `UNLOCK|LOAD_SECRETS` for all items of the schema, across all keyrings: of several copies of a key the one in the default keyring (`default_path`; `write()` stores there) counts, else the newest; a dismissed unlock prompt is no error for libsecret, the items come back locked without secrets, so `read_all()` raises "still locked" for a key it found only locked), Windows `CredentialManager` (ctypes `CredReadW`/`CredWriteW`/`CredDeleteW`, generic credentials `ChemAssistent/<key>`, UTF-16 blob, `CRED_PERSIST_ENTERPRISE`, `LOCAL_MACHINE` where a policy refuses that; a network logon such as SSH has no credential set, so the secrets stay in the file); `read`/`write`/`delete` raise `KeystoreError`. The Windows `--self-test` stores, reads and deletes one secret and checks `_save_lock()`. Uninstalling keeps the secrets like the config.
- `api_versions.py` (stdlib): the chemotionapi versions = release tags matching `TAG_PATTERN` (`v` + at least three digits; older tags like `0.3.32` are not supported), listed with `git ls-remote` (`list_tags()`, newest first by `version_key()`), `installed_tag()` from `workspace/chemotionapi.tag` (written by setup_workspace.sh and windows/build.py), `default_tag()` = `CHEMOTION_API_TAG`, else the installed one if still released, else the newest. As a script (`choose`/`default <workspace>`) it prints the tag for the installers; `choose` asks on stderr/stdin when stdin is a tty, and keeps the installed tag when offline. `workspace.system_prompt()` and gen_api_reference's header name the installed tag. The settings' Chemotion tab lists the tags and runs setup_workspace.sh with the chosen one (Linux only; the Windows bundle's version is `CHEMOTION_REF` in windows/build.py); in developer mode also the branches (`list_refs()` = one `ls-remote --tags --heads`, combo ids `branch:<name>`, `setup_workspace.sh --branch`). `installed_branch()`/`installed_label()` ("v312.0.1" or "branch x"); the installers only know tags (an installed branch is replaced by the default tag on reinstall).
- `gen_api_reference.py`: walks `docs/index.rst` of the chemotionapi checkout in toctree order, converts the reST lightly to Markdown and expands `autoclass`/`automodule`/`autoenum` with signatures and docstrings of the **installed** package (so it must run with the venv's Python). Install/docker-CLI sections are skipped (`SKIP_SECTIONS`).
- `jupyter.py` (no GTK; `requests` + `websocket-client`, imported inside `execute()`): `split_url()` (base URL + token from `…/lab?token=…`). `JupyterClient`: token → `Authorization: token`, password → `GET/POST login` with the `_xsrf` cookie, then `X-XSRFToken`; contents API (`ensure_dir`, `files()` recursive without dotfiles/checkpoints, `upload`/`download` base64, notebooks), `session(path)` (`POST api/sessions` returns the existing session of an open notebook → same kernel), `execute()` over `api/kernels/<id>/channels` (messaging protocol 5.3, iopub of our `msg_id` until `idle` + `execute_reply`; stream/execute_result/display_data PNG/error → nbformat `outputs`; timeout or `cancelled` → `interrupt`), `test()` for the settings. `JupyterBridge` (one per conversation, `lock`): remote folder `<jupyter_folder>/<conversation id>` with `analysis.ipynb` (`INTRO_CELLS` define `exchange` for manual runs), `run()` = ensure notebook → `sync_up` → session → silent `PREAMBLE` (defines `exchange` = the kernel's start cwd, `_ca_fresh` via `user_expressions` → `new_kernel` when the notebook had earlier runs) → execute → append the cell → `sync_down`. Sync state in `.sync.json` of the local folder (local size/mtime_ns, remote `last_modified`), no deletions, `MAX_TRANSFER_BYTES`; `jobs/` is never synced. `folder_lock()`: one lock per local folder, shared by the window's bridge and the job watcher's. Background jobs: `start_job()` writes `jobs/<id>.ipynb` (shows the code), starts a session for it (a new kernel, cwd `jobs/`) and sends `JOB_RUNNER` + the code with `JupyterClient.start()` (returns once the kernel is busy; the kernel keeps running after the websocket closes). `JOB_RUNNER` runs the code with `shell.run_cell()` inside the kernel: `exchange` = the conversation folder, prints into `jobs/<id>.log`, figures (`capture_output`) into `exchange` as `<id>_figure_<n>.png`, the outcome (state, result = repr of the last expression — `sys.displayhook` must be the shell's again inside `capture_output`, error with IPython's frames cut, output tail) atomically into `jobs/<id>.json`. `job_status()` reads that file; a job keeps its kernel busy until it wrote its outcome, so "running" with a kernel that is gone or not `busy` (Jupyter restarts a crashed/OOM-killed kernel under the same id) is `lost` (the file is re-read first, the job may just have ended); Jupyter Server may go on reporting the restarted kernel as `busy` for minutes, so every `JOB_PROBE_S` a "busy" job kernel gets a `kernel_info_request` (`JupyterClient.answers()`: the shell handles one request at a time, so only an idle kernel answers). `start_job()` closes the session again when `start()` fails (an unrecorded job has no owner). Sync hardening: `sync_down` never writes outside the local folder, `sync_up` skips symlinks; skipped files (too large, outside) are not recorded, so their note comes with every sync. `finish_job()` closes the session and syncs down. Tested against JupyterLab 4 / Jupyter Server 2 with token and password.
- `jobs.py` (no GTK): `Jobs` = the registry `STATE_DIR/jobs.json` (id, conversation, purpose, server, folder, kernel, notebook_url, state running/done/failed/lost/cancelled, `report`, `delivered`, `notified`, `wake`, `stopped`; delivered jobs dropped after `KEEP_S`) and the watcher thread (`_check()` every `POLL_S`, right after the app starts too): ended jobs get `finish_job()` and a `report()` for the agent; `on_change()` (→ `GLib.idle_add(app.jobs_changed)`) after starts, ends, problems and `mark_delivered()`. The watcher (one thread, `start()` guards) is the only one that ends a job, each final update conditional on the state it saw (`update(only_state=…)`); `cancel()` only marks the job `cancelling` (`ACTIVE` = running/cancelling) and wakes the watcher, which shuts the kernel down — also after a restart — and records `stopped` (a later round, e.g. after waiting for a busy exchange folder, then reports `cancelled`, not the interrupted job's `failed`/`lost`), or reports the real outcome if the job ended (done/failed) before; a cancelled job's report has `wake=False`: it goes with the user's next message instead of starting a turn. `info()` is the agent's `jupyter_jobs` tool (with the log tail of active jobs). A report keeps the end of the printed output (`REPORT_OUTPUT_CHARS`), so it fits into `agent.MAX_ANSWER_CHARS` (clipped from the start) with its last lines. Reports reach the agent as a user message starting with `REPORT_HEADER` (several joined by app's `REPORT_SEPARATOR`, a typed message after `USER_TEXT`); `ChatPanel.replay()` shows them as notes. Only one JupyterLab is checked: jobs on another server (settings changed) keep a `problem`.
- Developer mode (`developer_mode`, optional `github_token`; settings tab "Developer"): `issues.py` (stdlib) behind the `report_api_bug` tool (`agent.REPORT_API_BUG_TOOL`, `build_tools(…, developer)`; mcp_bridge.py offers it when the session file has `developer`, with `model` = `issues.model_label()`, and runs it with a fresh `load_config()`), `workspace.DEVELOPER_PROMPT` says to report every chemotion_api bug. `report()` appends an environment table the agent cannot get wrong (date, model, Chemotion URL + version/revision parsed from the ELN's public `/about` page — the REST API has no version endpoint —, chemotionapi label + commit + package version), saves it as Markdown in `ISSUES_DIR` (`STATE_DIR/issues`), and with a token creates it on GitHub (`REPO` from `api_versions.REPO_URL`; skipped when an open issue has the same normalized title), else answers with a prefilled `issues/new?title=…&body=…` link (body clipped to `MAX_URL_BODY_CHARS`) for the user. - `chemotion_runner.py`: stdin JSON → logs in (`Instance(url).test_connection().login()`), execs the snippet with `instance` (and with JupyterLab `exchange`, a `Path`) predefined and stdout/stderr captured, `to_jsonable()` converts `result` (elements/collections/users become small dicts via `describe_object()`; elements get `url` from chemotionapi's `element.url()`; lists capped at `MAX_ITEMS`), JSON on stdout.
- `model_picker.py` (GTK): the model chooser for lists of hundreds of models (the Gemini API also lists embedding/image/video/audio models): `ModelList` = `Gtk.SearchEntry` (all words must occur, Enter picks the first match, Down enters the list), "Only chat models" (hides `NON_CHAT` ids, shown only when there are some; the current model always shows) and a `Gtk.ListBox` in a `ScrolledWindow`; `prepare()`/`fit()` on the popover's `show` size the list to the room above/below the button (`MAX_LIST_HEIGHT`; a GTK 3 popover cannot leave its window) and open it on that side. `ModelEntry` = entry + `MenuButton` with a ModelList popover (the settings' model field). The header's model popover in app.py holds a ModelList plus a status label and "Load again".
- `settings.py`: ordinary GTK window like vikunja-popups' settings (Chemotion fields; AI section with an “Agent” combo (`AGENTS`) whose rows URL/token/command are shown per `AGENT_KEYS` (`no_show_all` + `set_visible`; the values of every agent are kept in `agent_values` while switching), `ai_url` combo offering the agent's URL (`AGENT_URLS`: KI-Toolbox, Gemini, Ollama), a warning label for `AGENT_WARNINGS`, secret `ai_token`, “Check” = `cli_agent.check_command()` (`--version`), model field (`ModelEntry`) filled by “Load models” = `agent.list_models()` in a thread, which also tests URL and token; tabs (`Gtk.Notebook`, `_page()`): Chemotion (“Test connection” logs in with chemotion_api in a thread), AI agent, JupyterLab, Running code, General; JupyterLab section with “Test JupyterLab” (`JupyterClient.test()` in a thread), `_form_values()` splits a token off a pasted URL; Start/Stop app through `app_control.py` = `systemctl --user` on `chem-assistent.service`). Saving needs no restart: the app reads the config per conversation.

## Testing notes
- `tests/` (pytest) covers the GTK-free modules; `tests/README.md` says how to run them. `tests/pdf_maker.py` writes tiny PDFs by hand (text per page plus a drawn line) for `test_documents.py` and the PDF/view_page tests; a picture-only PDF (no text layer) for checking that a model really sees an image can be made with pypdfium2 (`PdfImage` + `PdfBitmap.from_pil`). An autouse fixture `keyring` puts an in-memory `FakeKeyring` (`fail = True` raises, `on_read` runs inside `read_all()`, e.g. to wait like an unlock prompt) behind `keystore`, replaces `SecretService`/`CredentialManager` with `NoRealKeyring` (raises: no test reaches the user's keyring, also when `backend()` probes again) and resets keystore's probe state and config's cache, reader and main-thread wait; `no_keyring` simulates a system without one (`PROBE_RETRY_S` infinite). `SecretService.read_all()` is tested with stub items (`secret_service()` in test_config.py). The real libsecret backend can be tried under WSL in a private session: `XDG_DATA_HOME=<tmp> XDG_RUNTIME_DIR=<short tmp> dbus-run-session -- sh -c 'echo -n pw | gnome-keyring-daemon --unlock --components=secrets; …'` (the runtime dir must be short: AF_UNIX; without `DISPLAY`/`WAYLAND_DISPLAY` the unlock prompt of a locked collection fails at once, like a dismissed one, else gcr-prompter opens a window asking for that session's password, `pw`). `test_jupyter.py` starts a throwaway Jupyter server from `JUPYTER_TEST_BIN` (skipped without one). The AI model is simulated there by `tests/fake_ai.py`: a scripted OpenAI-compatible endpoint (SSE chunks, tool calls split across deltas, HTTP errors), so the agent's real code runs against prescripted answers.
- A local Chemotion test instance from chemotionapi's `test_config` (docker, port 3579) is useful; its login is in `~/Deveolop/KIT/chemotionapi/tests/config.json`. Never commit credentials. The Chemotion tests use it via the same file (auto-skip when it is down) and clean up every sample they create; the ELN REST API's `DELETE /api/v1/samples/<id>` works, collections cannot be deleted that way.
- JupyterLab: a scratch server is enough (`python3 -m venv jlab && jlab/bin/pip install jupyterlab rdkit matplotlib pandas`, `jupyter lab --no-browser --port 8899 --ServerApp.root_dir=… --IdentityProvider.token=test`; for password login `--PasswordIdentityProvider.hashed_password=$(python -c "from jupyter_server.auth import passwd; print(passwd('secret'))") --IdentityProvider.token=""`). pytest does not cover anything with GTK: test the window against the scratch server (patch `jobs.load_config`/`app.load_config`, `jobs.JOBS_FILE`, `history.HISTORY_DIR`/`EXCHANGE_DIR` to throwaway paths, `app.Notify = None`, and `Agent.send` with a stub for the window). chemotion_api has no method to delete elements; use the REST `DELETE` above or the web UI.
- The Windows bundle cannot be built or run here (PyInstaller does not cross-compile); its only automated check is `chem-assistent-runner.exe --self-test` in `windows/build.py`, i.e. the GitHub workflow.
- WSL (WSLg) works for testing from the source tree (`--show`; no indicator, hotkey or systemd). Ubuntu 22.04's Python 3.10 is too old for chemotion_api: a `python3.14` venv **without** `--system-site-packages` (the shared `dist-packages` has the 3.10 `gi`) with `pip install "PyGObject<3.51" pycairo` (GLib 2.72 has no girepository-2.0; needs `libgirepository1.0-dev libcairo2-dev`), and `adwaita-icon-theme-full` for a mouse pointer. Do not open X11 GTK windows there and type into them (test scripts with `GDK_BACKEND=x11`): that hides the pointer for the whole WSLg session.
- Under rootless XWayland the root window cannot be captured; capture the app's own window with `Gdk.pixbuf_get_from_window(window.get_window(), ...)`.
