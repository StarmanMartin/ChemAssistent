# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
A small Ubuntu desktop app (Python 3, GTK 3 via PyGObject). A Chemotion icon in the GNOME top bar (Ayatana AppIndicator) opens a centered prompt; submitting it grows the window to the work area with a chat (`ChatPanel`) on the left and a result panel on the right. The agent is our own (`agent.py`, stdlib only) and talks to any OpenAI-compatible API (default: the KIT KI-Toolbox, or a local Ollama); the settings can instead pick a CLI agent (`cli_agent.py`: Claude Code, Codex) with the same tools. The agent reaches the Chemotion ELN only through its `execute_python` tool, whose code the user must confirm in the result panel — unless an auto-run mode is on (`config.AUTO_RUN_MODES`: `off`/`readonly`/`always`; `readonly` auto-runs snippets that `agent.looks_read_only()` clears). With a JupyterLab configured the built-in agent also has `execute_jupyter` (`jupyter.py`) for analyses and `start_jupyter_job` for long calculations (background jobs, `jobs.py`; their reports come back as a new turn), and both sides share a per-conversation exchange folder. Structure, config handling, settings app and install scripts are taken over from `~/Deveolop/private/vikunja-popups`. Until 2026-10 the app embedded the opencode TUI instead (see git history). There is no linter config; the tests are `tests/` (pytest, see below); only the Windows version has a build step (`windows/build.py`, see below).

## Commands
- Run from the source tree: `.venv/bin/python app.py --show` (`--show` opens the prompt at start; a second start sends `{"type": "show"}` over the socket to the running instance instead).
- Tests: `.venv/bin/pip install pytest` (once), then `.venv/bin/python -m pytest tests/` (see `tests/README.md`). The AI is simulated (`tests/fake_ai.py`, a scripted OpenAI-compatible endpoint); the Chemotion tests run against the local test instance (docker, port 3579) and auto-skip when it is down. Everything they create there goes into `AIExamples/ChemAssistent tests` and is deleted again.
  - The venv must be created with **`/usr/bin/python3`** `-m venv --system-site-packages .venv` (an asdf/pyenv `python3` on the PATH has no `gi`), then `.venv/bin/pip install -r requirements.txt` and `./setup_workspace.sh "$PWD" "$PWD/.venv/bin/python"`, which clones a chemotionapi release tag (optional 3rd argument; default: `api_versions.py default`; or `--branch <name>` for a branch head) (with its `skills/`) into `workspace/chemotionapi`, pip-installs it, writes `workspace/CHEMOTION_API.md` and records the tag in `workspace/chemotionapi.tag` (a branch in `workspace/chemotionapi.branch` instead; the other file is removed).

A new file must be added to `APP_FILES`.

## Architecture
- Platform split: `config.WINDOWS`; `config.FROZEN` is the PyInstaller build (this file's folder is then `_internal\`, so `HERE`, `WORKSPACE_DIR` and the SVGs resolve inside the bundle). Windows has no AppIndicator (`Gtk.StatusIcon`), no AF_UNIX in Python and no unix signals (`signal_add` is `None`). On Windows `main()` logs to `STATE_DIR/app.log` and writes the PID file (`app_control.py`, used by the settings' Start/Stop; `APP_PROCESS_NAMES`). Child processes (settings, runner, the app from the settings) start through `workspace.command(script, console)`: from source the current Python (python.exe/pythonw.exe on Windows), frozen the exes in `FROZEN_PROGRAMS`; the runner gets `creationflags=NO_WINDOW`. Otherwise the UI is the same on both platforms.
- `ipc.py`: for a second start of the app (`{"type": "show"}`), hotkey.py (`{"type": "hotkey"}`) and mcp_bridge.py (`{"type": "execute", "session", "purpose", "code"}`, answered with `{"text"}` once the card is decided; `RequestServer._serve` drops the 5 s timeout for it, `MAX_REQUEST_BYTES` is large for the code). Linux: Unix socket `SOCKET_PATH`, empty token. Windows: `127.0.0.1:<random port>` plus a random token, both in `ENDPOINT_FILE`; requests without the right token are dropped.
- `config.py`: `~/.config/chem-assistent/config.json` (Windows: `%APPDATA%`, state in `%LOCALAPPDATA%`) (0600, atomic writes), `load_config()` raises `ValueError` while URL/user/password are missing (`config_problem()`); `CHEMOTION_PASSWORD` overrides the password. AI: `ai_url` (default `KI_TOOLBOX_URL`), `ai_token` (empty → env `KI_TOOLBOX_API_KEY`, `ai_token()`), `ai_model` (default `alias.complex-local`); `ai_problem()` is checked on submit and in the settings. `auto_run` is one of `AUTO_RUN_MODES` (unknown values → `off`) and the default mode for new conversations. JupyterLab (optional): `jupyter_url` (empty = off; `load_config()` also empties it while `jupyter_problem()` complains), `jupyter_token` or `jupyter_password`, `jupyter_folder` (default `DEFAULT_JUPYTER_FOLDER`), `jupyter_verify_tls`; `Config.jupyter`. `EXCHANGE_DIR` = `STATE_DIR/exchange`. `agent` is one of `AGENTS` (`api`, `ollama`, `claude`, `codex`); each keeps its own keys (`AGENT_KEYS`: `ollama_url`/`ollama_model`, `<cli>_command`/`<cli>_model`), and `load_config()` puts the chosen one's into `Config.ai_url`/`ai_token`/`ai_model`/`agent_command` (so Ollama is just the built-in agent with another URL and no token). An empty CLI model is the CLI's default (`model_name()`); `cli_agent.cli_models()` fills the header menu (`CLI_MODELS` plus the `visibility: "list"` slugs of Codex's `~/.codex/models_cache.json`). The app starts anyway and reports problems in the prompt. `WORKSPACE_DIR` is `workspace/` next to the code; `SOCKET_PATH` is in `$XDG_RUNTIME_DIR` (AF_UNIX paths are limited to ~100 bytes).
- `api_versions.py` (stdlib): the chemotionapi versions = release tags matching `TAG_PATTERN` (`v` + at least three digits; older tags like `0.3.32` are not supported), listed with `git ls-remote` (`list_tags()`, newest first by `version_key()`), `installed_tag()` from `workspace/chemotionapi.tag` (written by setup_workspace.sh and windows/build.py), `default_tag()` = `CHEMOTION_API_TAG`, else the installed one if still released, else the newest. As a script (`choose`/`default <workspace>`) it prints the tag for the installers; `choose` asks on stderr/stdin when stdin is a tty, and keeps the installed tag when offline. `workspace.system_prompt()` and gen_api_reference's header name the installed tag. The settings' Chemotion tab lists the tags and runs setup_workspace.sh with the chosen one (Linux only; the Windows bundle's version is `CHEMOTION_REF` in windows/build.py); in developer mode also the branches (`list_refs()` = one `ls-remote --tags --heads`, combo ids `branch:<name>`, `setup_workspace.sh --branch`). `installed_branch()`/`installed_label()` ("v312.0.1" or "branch x"); the installers only know tags (an installed branch is replaced by the default tag on reinstall).
- `gen_api_reference.py`: walks `docs/index.rst` of the chemotionapi checkout in toctree order, converts the reST lightly to Markdown and expands `autoclass`/`automodule`/`autoenum` with signatures and docstrings of the **installed** package (so it must run with the venv's Python). Install/docker-CLI sections are skipped (`SKIP_SECTIONS`).
- `jupyter.py` (no GTK; `requests` + `websocket-client`, imported inside `execute()`): `split_url()` (base URL + token from `…/lab?token=…`). `JupyterClient`: token → `Authorization: token`, password → `GET/POST login` with the `_xsrf` cookie, then `X-XSRFToken`; contents API (`ensure_dir`, `files()` recursive without dotfiles/checkpoints, `upload`/`download` base64, notebooks), `session(path)` (`POST api/sessions` returns the existing session of an open notebook → same kernel), `execute()` over `api/kernels/<id>/channels` (messaging protocol 5.3, iopub of our `msg_id` until `idle` + `execute_reply`; stream/execute_result/display_data PNG/error → nbformat `outputs`; timeout or `cancelled` → `interrupt`), `test()` for the settings. `JupyterBridge` (one per conversation, `lock`): remote folder `<jupyter_folder>/<conversation id>` with `analysis.ipynb` (`INTRO_CELLS` define `exchange` for manual runs), `run()` = ensure notebook → `sync_up` → session → silent `PREAMBLE` (defines `exchange` = the kernel's start cwd, `_ca_fresh` via `user_expressions` → `new_kernel` when the notebook had earlier runs) → execute → append the cell → `sync_down`. Sync state in `.sync.json` of the local folder (local size/mtime_ns, remote `last_modified`), no deletions, `MAX_TRANSFER_BYTES`; `jobs/` is never synced. `folder_lock()`: one lock per local folder, shared by the window's bridge and the job watcher's. Background jobs: `start_job()` writes `jobs/<id>.ipynb` (shows the code), starts a session for it (a new kernel, cwd `jobs/`) and sends `JOB_RUNNER` + the code with `JupyterClient.start()` (returns once the kernel is busy; the kernel keeps running after the websocket closes). `JOB_RUNNER` runs the code with `shell.run_cell()` inside the kernel: `exchange` = the conversation folder, prints into `jobs/<id>.log`, figures (`capture_output`) into `exchange` as `<id>_figure_<n>.png`, the outcome (state, result = repr of the last expression — `sys.displayhook` must be the shell's again inside `capture_output`, error with IPython's frames cut, output tail) atomically into `jobs/<id>.json`. `job_status()` reads that file; a job keeps its kernel busy until it wrote its outcome, so "running" with a kernel that is gone or not `busy` (Jupyter restarts a crashed/OOM-killed kernel under the same id) is `lost` (the file is re-read first, the job may just have ended); Jupyter Server may go on reporting the restarted kernel as `busy` for minutes, so every `JOB_PROBE_S` a "busy" job kernel gets a `kernel_info_request` (`JupyterClient.answers()`: the shell handles one request at a time, so only an idle kernel answers). `start_job()` closes the session again when `start()` fails (an unrecorded job has no owner). Sync hardening: `sync_down` never writes outside the local folder, `sync_up` skips symlinks; skipped files (too large, outside) are not recorded, so their note comes with every sync. `finish_job()` closes the session and syncs down. Tested against JupyterLab 4 / Jupyter Server 2 with token and password.
- `jobs.py` (no GTK): `Jobs` = the registry `STATE_DIR/jobs.json` (id, conversation, purpose, server, folder, kernel, notebook_url, state running/done/failed/lost/cancelled, `report`, `delivered`, `notified`, `wake`, `stopped`; delivered jobs dropped after `KEEP_S`) and the watcher thread (`_check()` every `POLL_S`, right after the app starts too): ended jobs get `finish_job()` and a `report()` for the agent; `on_change()` (→ `GLib.idle_add(app.jobs_changed)`) after starts, ends, problems and `mark_delivered()`. The watcher (one thread, `start()` guards) is the only one that ends a job, each final update conditional on the state it saw (`update(only_state=…)`); `cancel()` only marks the job `cancelling` (`ACTIVE` = running/cancelling) and wakes the watcher, which shuts the kernel down — also after a restart — and records `stopped` (a later round, e.g. after waiting for a busy exchange folder, then reports `cancelled`, not the interrupted job's `failed`/`lost`), or reports the real outcome if the job ended (done/failed) before; a cancelled job's report has `wake=False`: it goes with the user's next message instead of starting a turn. `info()` is the agent's `jupyter_jobs` tool (with the log tail of active jobs). A report keeps the end of the printed output (`REPORT_OUTPUT_CHARS`), so it fits into `app.MAX_ANSWER_CHARS` (clipped from the start) with its last lines. Reports reach the agent as a user message starting with `REPORT_HEADER` (several joined by app's `REPORT_SEPARATOR`, a typed message after `USER_TEXT`); `ChatPanel.replay()` shows them as notes. Only one JupyterLab is checked: jobs on another server (settings changed) keep a `problem`.
- Developer mode (`developer_mode`, optional `github_token`; settings tab "Developer"): `issues.py` (stdlib) behind the `report_api_bug` tool (`agent.REPORT_API_BUG_TOOL`, `build_tools(…, developer)`; mcp_bridge.py offers it when the session file has `developer`, with `model` = `issues.model_label()`, and runs it with a fresh `load_config()`), `workspace.DEVELOPER_PROMPT` says to report every chemotion_api bug. `report()` appends an environment table the agent cannot get wrong (date, model, Chemotion URL + version/revision parsed from the ELN's public `/about` page — the REST API has no version endpoint —, chemotionapi label + commit + package version), saves it as Markdown in `ISSUES_DIR` (`STATE_DIR/issues`), and with a token creates it on GitHub (`REPO` from `api_versions.REPO_URL`; skipped when an open issue has the same normalized title), else answers with a prefilled `issues/new?title=…&body=…` link (body clipped to `MAX_URL_BODY_CHARS`) for the user. Issues are public: the tool description and prompt forbid ELN data and credentials.
- `lessons.py` (stdlib): `LESSONS_FILE` = `STATE_DIR/lessons.md`, shared by all conversations: one `## <key>` entry per lesson (date · topic · chemotionapi commit from `api_commit()`, read from `.git` without git), text before the first heading kept (hand edits). `save_lesson()` (the agent's `save_lesson` tool; same key replaces, `MAX_LESSON_CHARS`, slug keys, `TOPICS`, no `## ` in the text; the oldest entries go above `MAX_LESSONS_CHARS`), `remove_lesson()`, `write_text()` (atomic, 0600; also the settings' "Lessons" tab, which refuses to overwrite a file the agent changed meanwhile), `prompt_section()`. `workspace.system_prompt()` appends `LESSONS_PROMPT` (when to save, no ELN/user data) and the file (concatenated, not formatted: lessons may contain braces). `Agent._dispatch` adds `LESSON_REMINDER` to the first successful execute_* answer after a failed one since the user's last message (`failed_run`; recognized by `RAN_TEXT`/`FAILED_TEXT`, which app's `_answer_text()` uses). Tests get their own file (autouse fixture `lessons_file`).
- `skills/jupyter-calculations/` (the app's own agent skill, installed as a folder via `APP_DIRS` in install.sh and the spec's `datas`): which standard calculations work in JupyterLab with pip packages (RDKit, tblite GFN2-xTB, ASE, PySCF + pyscf-properties, MACE/ANI, PyXtal, python-docx), a ✅/⚠/❌ table with tested accuracy and times, and `references/` (`setup.md` helpers + install lines + background-job pattern, `xtb.md`, `dft.md`, `more.md`). Every code block was run in order like a notebook; keep it that way when editing (extract the ```python blocks of setup.md + one reference file and exec them in one namespace with `exchange` set). Known limits found in testing: raw GFN2 redox/anion energies are several eV off (use DFT), DFT-NMR in pyscf-properties fails with PySCF 2.14 (GIAO-HF works), Architector needs conda-only xtb-python, torchani needs `--no-deps` on Python 3.14.
- `history.py` (stdlib): one JSON file per conversation in `STATE_DIR/history` (0600 via `write_private_json`; title, model, `messages` = `Agent.messages` without the system prompt, `roots` = attachments, `agent`, `session` = a CLI agent's own session id), the newest `MAX_CONVERSATIONS` kept. The app saves after every turn (done/error/stopped) and on close, only when the message count changed; `entries()` feeds the prompt's “Recent conversations” list (`RECENT_CONVERSATIONS`), `clear()` the settings' “Clear history” button. Deleting/pruning a conversation also removes its local exchange folder (`exchange_dir(id)`); `clear()` removes all of `EXCHANGE_DIR`.
- `workspace.py`: `SYSTEM_PROMPT` (an f-string formatted again with `skills=`, so literal braces are quadrupled; `system_prompt(exchange)` appends `JUPYTER_PROMPT` with JupyterLab on (else `NO_JUPYTER_PROMPT`: say analyses need JupyterLab, no workarounds — models otherwise pip-install into the app's venv; the base prompt and the execute_python description forbid installs/subprocesses): the fetch → analyse → write-back workflow, and that Jupyter code must use the predefined `exchange`, never a local path — models otherwise hard-code the local path they are shown) plus `skill_lines(jupyter)`, which lists `workspace/chemotionapi/skills/*/SKILL.md` with the `description` from their front matter (and with JupyterLab on the app's own `skills/*/SKILL.md` = `config.SKILLS_DIR`, by absolute path; `Agent` then adds `SKILLS_DIR` to its roots); the agent reads them on demand.
- `agent.py` (no GTK, stdlib `urllib` only, standard OpenAI-compatible endpoints only): `list_models()` = `GET /models` (Open WebUI's `info.meta.hidden` models dropped; the KI-Toolbox needs ~15 s for it). `Agent.send()` runs in a worker thread: streamed `POST /chat/completions` with `tools`, SSE parsing (falls back to a plain JSON answer), tool-call deltas merged by `index`, `reasoning_content` kept and sent back (DeepSeek), at most `MAX_ROUNDS` tool rounds per message. Tools: `execute_python` (callback into the app, blocks until it is decided; the tool description comes from `execute_python_tool(mode)`, so it matches the current auto-run mode — `Agent.set_auto_run()` rebuilds it when the header menu changes the mode mid-conversation), `execute_jupyter`, `start_jupyter_job` and `jupyter_jobs` only with `Agent(exchange=…)` (`build_tools(mode, jupyter)`; the first two use the same `execute` callback with `target="jupyter"`/`"job"`, `jupyter_jobs` calls `Agent(jobs=…)`; the exchange folder is added to `roots`), read-only `read_file`/`grep`/`list_files` confined to `Agent.roots` (`_resolve()`: `WORKSPACE_DIR` plus every attachment of the conversation; relative paths are workspace paths, attachments are addressed by absolute path; binary files are only described). `send(text, attachments)` adds the attachments to `roots` and appends `ATTACHMENT_NOTE` and their absolute paths with `describe_attachment()` to the user message (`ChatPanel.replay()` splits on it). `restore()` continues a saved conversation behind the current system prompt and answers open tool calls. `set_model()` switches the model mid-conversation (the worker drops `reasoning_content` before the next request); `retry()` repeats the request after an error without a new user message (`send()`/`retry()` share `_run()`). Events go out through `on_event(kind, data)`: text/thinking/tool/done/error/stopped. `cancel()` closes the HTTP response; `_close_open_calls()` answers every unanswered tool call, or the next request is refused. Tested with the KI-Toolbox's `alias.complex-local` (GLM), `alias.medium-local` (DeepSeek), `alias.complex-gpt` and `alias.complex-claude`.
- `cli_agent.py` (no GTK, stdlib): `CliAgent` has `Agent`'s interface (without the JupyterLab tools: the app gives CLI agents no exchange folder) (`messages` hold only plain user/assistant texts, so both restore each other's conversations). Each message runs the CLI once in `WORKSPACE_DIR` (own session, prompt on stdin, killed as a process tree by `cancel()`), with a temp dir in `STATE_DIR` for the bridge's session file (ipc address/token, `session_token`, auto-run mode, roots), Claude's `--mcp-config` and `--system-prompt-file`. Claude: `-p --output-format stream-json --verbose --include-partial-messages --tools "" --allowedTools mcp__chemotion --permission-mode dontAsk --strict-mcp-config`, `--resume <session_id>`, `MCP_TOOL_TIMEOUT`. Codex: `codex exec [resume <thread_id>] --json --skip-git-repo-check -c …` (read-only sandbox, `approval_policy=never`, `CODEX_DISABLED_FEATURES` via `-c features.x=false` — `--disable` fails on unknown names, `-c` only warns —, the bridge as `mcp_servers.chemotion` with `default_tools_approval_mode="approve"` and a long `tool_timeout_sec`, the system prompt as `developer_instructions`, or in the first prompt for a Windows `.cmd` shim). `find_command()` also looks in the usual install dirs (the systemd service's PATH is short; nvm), `child_env()` puts the program's dir first on the PATH. A saved conversation resumes the CLI session only with the same CLI, else the CLI gets a transcript (`CONTEXT_NOTE`). Tested with Claude Code 2.1 and codex-cli 0.162 (Codex runs its tools through a JS `functions.exec` isolate without fs/network; `apply_patch` stays listed but the read-only sandbox refuses it).
- `mcp_bridge.py` (stdlib): the stdio MCP server the CLIs start (`workspace.command("mcp_bridge.py")`, frozen `chem-assistent-runner.exe --mcp-bridge`): `execute_python` (description from `execute_python_tool(mode)`) forwarded to the app over ipc.py, and agent.py's `read_file`/`grep`/`list_files` on the session file's roots. The app (`execute_for_bridge()`) accepts a call only with the open conversation's `session_token` and runs it through `AssistantWindow._execute()`, i.e. the same card and auto-run logic as the built-in agent.
- `app.py`:
  - `RequestServer`: accept thread for ipc.py (only `show`). `PendingRequest`: one `execute_python` call, a `threading.Event` the card sets via `answer()`; `AssistantWindow._execute()` (agent thread) waits on it and abandons it when the agent is cancelled.
  - `AssistantWindow`: one undecorated window; a `Gtk.Stack` with the prompt page and, after submit, the conversation page (header bar, `Gtk.Paned` with `ChatPanel` + `ResultsPanel`, `CHAT_SHARE`). `_grow()` animates move/resize to `work_area()` and then maximizes. The window is DIALOG-type/keep-above while it is a prompt and drops keep-above/skip-taskbar when expanded. Escape closes the prompt, and in the conversation stops a busy agent. The header's model menu switches the conversation's model (not the config; a "Model: x" note goes into the chat); its list comes from `ChemAssistentApp.load_models()` (`list_models()` in a thread, once per `ai_url`/`ai_token`, "Load again" after an error). An error note gets Retry (`_retry()` → `Agent.retry()`) and "Change model…" buttons (`ChatPanel.add_note(actions=…)`, disabled by the next message or `clear_actions()`). Agent events reach the main loop through `GLib.idle_add` (`_on_agent_event`); `closed` guards events after the window is gone. Focus uses `GdkX11.x11_get_server_time()` because menu activations from the top bar arrive over D-Bus without an event time. Closing cancels the agent and rejects waiting cards.
  - `ChatPanel`: messages in a scrolled box (`BottomFollower` keeps it at the bottom), streamed answers re-rendered at most every 60 ms with `markdown_markup()` (code blocks, aligned tables, headings, lists, inline code, bold, links → Pango markup; validated with `Pango.parse_markup`, else plain text), notes for tools and code cards, status line with spinner, multi-line input (Enter sends, Shift+Enter newline), Send/Stop, a paperclip `Gtk.MenuButton` (File…/Folder… via `Gtk.FileChooserNative`) and drag and drop of `text/uri-list` onto the panel (the text view's own drop target is unset) collect attachments as chips in an `Attachments` (`Gtk.FlowBox`); they go with the next message. The prompt page has the same paperclip and drop target (its own `Attachments`); they go with the first message (`_start_conversation(attachments=…)`).
  - JupyterLab: `_start_conversation()` creates `JupyterBridge` + `exchange` (`history.exchange_dir()`) when `config.jupyter`; `_show_request()` sets `pending.new_execution` (`Execution(code, exchange)` or `JupyterExecution(code, purpose, bridge)`, same `run()`/`cancel()` interface) and never auto-runs Jupyter code in `readonly`. Jupyter settings that are set but incomplete (`jupyter_problem()`) give a warning note at the start of the conversation. `Execution` passes `exchange` to the runner and saves a `result` as `chemotion_result_<n>.json`; `JupyterExecution` saves PNG outputs as `figure_<n>.png` (`free_name()`, `bridge.mark_local()` so they are not uploaded). `result_page(…, outcome)` adds figures (`image_widget()`, `MAX_IMAGE_WIDTH`), exchanged files (open on click) and the notebook link (`exchange_section()`); `_answer_text()` tells the agent about new kernels, figures and exchanged files.
  - Background jobs: `target="job"` cards create a `JobExecution` (starts the job through `ChemAssistentApp.jobs`, answers at once with the job id; auto-run as for Jupyter code). The header's jobs button (hidden without jobs, `_fill_jobs_menu()`, refreshed every `JOB_MENU_REFRESH_S`) lists the conversation's jobs with notebook link and Cancel. `_deliver_jobs()` sends undelivered reports as a new turn when the agent is idle (on `jobs_changed()`, after a `done` turn, and right after a conversation is continued from the history); `_send()` puts reports without `wake` in front of the user's message. `ChemAssistentApp.jobs_changed()` drops reports of deleted conversations, notifies (libnotify `Notify`, if installed; not on Windows) about ended jobs of conversations that are not open or not active — the action calls `open_conversation()`, which switches conversations (a busy or waiting one gets a "Switch to it" note instead) — and keeps the top-bar menu entries (`_update_job_items()`: "Job done: … – continue…", "n background jobs running") current; the prompt's recent list shows "job finished"/"job running".
  - `RequestCard`: editable code (GtkSourceView 4 if installed, else `TextView`), Run / Reject with optional reason, then a status line (the output goes to a result tab). `Execution` runs `chemotion_runner.py` with the venv Python in its own session (killable, `execution_timeout`), reading fresh credentials with `load_config()`. The answer to the agent says whether the user edited the code (and includes the code that ran), the output, `result` as JSON, clipped to `MAX_ANSWER_CHARS`. Auto-run: `_show_request()` decides on the main loop with the window's current mode — `always` sets `pending.auto`, `readonly` only if `looks_read_only(pending.code)` clears the code (otherwise the card keeps the skip reason in its status line); an auto card locks the editor, gets an "auto" badge and runs itself on the next idle tick, everything downstream (Execution, result tab, `pending.answer`) is unchanged. If the agent stops while an auto card runs, `_on_abandoned()` kills the execution (manual runs are left alone: the user clicked Run).
  - `ResultsPanel`: a vertical `Gtk.Paned`; on top only the newest `RequestCard` (older cards stay only while waiting/running, `_prune()`), below a `Gtk.Notebook` with one tab per finished run (`result_page()`: output, error, result; at most `MAX_RESULT_TABS`).
  - `result_widget()`: list of dicts → table (max `MAX_TABLE_COLUMNS`), dict → key/value table, dict with list/dict values → one section per key, list of scalars → one column, else text. Dicts with a `"url"` (every element from the runner) are rows with a link icon that open the URL in the browser on a single click (`open_url()`, `webbrowser`).
  - Display: `GDK_BACKEND=x11` is forced whenever `DISPLAY` is set, because Mutter ignores client positioning on Wayland — except under WSLg (`WSLG`: `WSL_DISTRO_NAME` and `WAYLAND_DISPLAY`): once an X11 client sets GTK's blank “hide while typing” cursor, WSLg shows no pointer over any X11 window until `wsl --shutdown`, so there the Wayland backend is used and `_grow()` only maximizes (no animation on a `GdkWaylandDisplay`). Menus in the window (model, auto-run, paperclip) are popovers (`menu_popover()`, `Gtk.ModelButton` rows; the callback runs on idle because it may rebuild the popover), not `Gtk.Menu`: on Wayland GDK refuses to map a menu while the button's tooltip is the topmost popup ("Tried to map a popup with a non-top most parent"), and the invisible menu's grab freezes the window. Only the indicator/tray menu (`_build_menu()`) is a `Gtk.Menu`. The dark theme variant is requested. `gi.require_version("Gdk", "3.0")` is needed because Gdk is imported before Gtk.
  - Top bar: the GNOME AppIndicator extension never sends a plain left click to Ayatana indicators (left click opens the menu, middle click → `SecondaryActivate`), so the first menu entry “Ask Chemotion…” is also the secondary-activate target. The icon is `chem-assistent-panel.svg` found via `set_icon_theme_path(HERE)`. Icons: the Chemotion mark (two open rings as exact arc paths, the red "c" traced from the original PNG) in `chem-assistent.svg` (dark-gray outer ring; desktop/menu, window icon, Windows .ico and tray, `docs/assets/logo.svg`) and `chem-assistent-panel.svg` (light outer ring `#e6e6e6`; top bar, the app's dark prompt/header via `DARK_UI_ICON_FILE`, the presentation's cover slide inline). Keep them in sync. Without the AppIndicator typelib the app logs a warning and opens the prompt.
- `hotkey.py` (stdlib at module level; GNOME runs it on every press, ~50 ms): global hotkey `hotkey` (default `<Control>space`, `""` = off). GNOME/Wayland allows no global grabs, so `register_gnome()` writes a custom keybinding (`GNOME_BINDING_PATH`, command = this interpreter + `hotkey.py`) via Gio.Settings: at app start (`_register_hotkey()`, so the last started copy owns it) and on save in the settings. Run without arguments it sends `{"type": "hotkey"}` over ipc.py; the app's `hotkey_pressed()` opens the prompt on two presses within `HOTKEY_DOUBLE_S`. `--unregister` (uninstall.sh) removes the binding. Windows: `listen_windows()` = `RegisterHotKey` + message loop in a thread, key from `virtual_key()` (space, a-z, 0-9, F1-F12), registered at app start only. The grab means a single Ctrl+Space no longer reaches other apps.
- `chemotion_runner.py`: stdin JSON → logs in (`Instance(url).test_connection().login()`), execs the snippet with `instance` (and with JupyterLab `exchange`, a `Path`) predefined and stdout/stderr captured, `to_jsonable()` converts `result` (elements/collections/users become small dicts via `describe_object()`; elements get `url` from chemotionapi's `element.url()`; lists capped at `MAX_ITEMS`), JSON on stdout.
- `settings.py`: ordinary GTK window like vikunja-popups' settings (Chemotion fields; AI section with an “Agent” combo (`AGENTS`) whose rows URL/token/command are shown per `AGENT_KEYS` (`no_show_all` + `set_visible`; the values of every agent are kept in `agent_values` while switching), `ai_url` combo offering the KI-Toolbox (or Ollama) URL, secret `ai_token`, “Check” = `cli_agent.check_command()` (`--version`), model combo filled by “Load models” = `agent.list_models()` in a thread, which also tests URL and token; tabs (`Gtk.Notebook`, `_page()`): Chemotion (“Test connection” logs in with chemotion_api in a thread), AI agent, JupyterLab, Running code, General; JupyterLab section with “Test JupyterLab” (`JupyterClient.test()` in a thread), `_form_values()` splits a token off a pasted URL; Start/Stop app through `app_control.py` = `systemctl --user` on `chem-assistent.service`). Saving needs no restart: the app reads the config per conversation.

## Testing notes
- `tests/` (pytest) covers the GTK-free modules; `tests/README.md` says how to run them. `test_jupyter.py` starts a throwaway Jupyter server from `JUPYTER_TEST_BIN` (skipped without one). The AI model is simulated there by `tests/fake_ai.py`: a scripted OpenAI-compatible endpoint (SSE chunks, tool calls split across deltas, HTTP errors), so the agent's real code runs against prescripted answers.
- A local Chemotion test instance from chemotionapi's `test_config` (docker, port 3579) is useful; its login is in `~/Deveolop/KIT/chemotionapi/tests/config.json`. Never commit credentials. The Chemotion tests use it via the same file (auto-skip when it is down) and clean up every sample they create; the ELN REST API's `DELETE /api/v1/samples/<id>` works, collections cannot be deleted that way.
- JupyterLab: a scratch server is enough (`python3 -m venv jlab && jlab/bin/pip install jupyterlab rdkit matplotlib pandas`, `jupyter lab --no-browser --port 8899 --ServerApp.root_dir=… --IdentityProvider.token=test`; for password login `--PasswordIdentityProvider.hashed_password=$(python -c "from jupyter_server.auth import passwd; print(passwd('secret'))") --IdentityProvider.token=""`). pytest does not cover anything with GTK: test the window against the scratch server (patch `jobs.load_config`/`app.load_config`, `jobs.JOBS_FILE`, `history.HISTORY_DIR`/`EXCHANGE_DIR` to throwaway paths, `app.Notify = None`, and `Agent.send` with a stub for the window). chemotion_api has no method to delete elements; use the REST `DELETE` above or the web UI.
- The Windows bundle cannot be built or run here (PyInstaller does not cross-compile); its only automated check is `chem-assistent-runner.exe --self-test` in `windows/build.py`, i.e. the GitHub workflow.
- WSL (WSLg) works for testing from the source tree (`--show`; no indicator, hotkey or systemd). Ubuntu 22.04's Python 3.10 is too old for chemotion_api: a `python3.14` venv **without** `--system-site-packages` (the shared `dist-packages` has the 3.10 `gi`) with `pip install "PyGObject<3.51" pycairo` (GLib 2.72 has no girepository-2.0; needs `libgirepository1.0-dev libcairo2-dev`), and `adwaita-icon-theme-full` for a mouse pointer. Do not open X11 GTK windows there and type into them (test scripts with `GDK_BACKEND=x11`): that hides the pointer for the whole WSLg session.
- Under rootless XWayland the root window cannot be captured; capture the app's own window with `Gdk.pixbuf_get_from_window(window.get_window(), ...)`.
